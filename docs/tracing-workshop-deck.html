The problem

Logs from four services
tell you nothing about one request.

A request touches many services. Each logs separately. When something is slow, you manually correlate timestamps across multiple streams — if you can find the right lines at all.

At scale, timing and concurrency problems are effectively invisible in logs.

Part 1
The answer

A trace assembles the
execution structure for you.

A trace represents a single request as it travels through a distributed system. It is made up of spans — units of work, each with a start time, end time, and structured attributes.

The execution structure is assembled automatically. You read it, you don't reconstruct it.

Part 1
How we got here

Every tracer today is built
on three fields from 2010.

2010

Google Dapper

Invented the model: traceId · spanId · parentId. Those three fields are in the traceparent header your services use right now.

2012

Twitter Zipkin

Open-sourced the Dapper model. First widely-adopted tracing system.

2017

Uber Jaeger

Built when Zipkin's storage layer couldn't handle 2,000+ services at Uber's scale. Now a CNCF project.

2019

OpenTelemetry

OpenTracing + OpenCensus merged. One vendor-neutral standard for traces, metrics, and logs. What this workshop uses.

2021

W3C TraceContext

Dapper's three fields became an official web standard. Interoperable across every vendor and language.

The point

The model is 15 years old and entirely stable. The tooling has changed; the three core concepts have not.

Every backend — Jaeger, Tempo, Zipkin, Honeycomb, Datadog, AWS X-Ray — is a different storage and UI layer on top of the same Dapper model. Once you understand spans and trace context, you understand all of them.

Part 1
Production usage

At scale, traces replace hours
of log archaeology with seconds.

Netflix — session failure reconstruction

A member tweets: "Why doesn't Tiger King play?" Before traces, engineers sifted through logs from CDN, auth, device, and streaming services manually. With a session trace ID, the full failure path — every service, every hop, every retry — is in one view in seconds. Netflix TechBlog, 2020

Uber — dynamic sampling at 2,000+ services

"More people take rides during peak hours — a fixed sampling probability might be too low off-peak, yet too high at peak." Uber built dynamic backend-controlled rates that adjust for traffic seasonality and per-service downstream fanout — things individual services can't see. Uber Engineering, 2017

Netflix Telltale — alert routing via trace topology

Telltale monitors 100+ production applications by combining traces, metrics, deployment events, and canary data into one health model. If the root cause is in an upstream service, Telltale routes the alert to that team automatically — using service topology derived from traces, not manual config. Netflix TechBlog, 2020

Netflix — engineers explored <1% of traces

Netflix measured how their Edgar tracing platform was actually used. Less than 1% of collected traces were ever opened. Nobody looks at healthy fast traces. This is the strongest argument for tail-based sampling: store only what matters. Netflix TechBlog, 2020

Part 1
Two traps that traces solve

A successful call
can still be slow or wrong.

Mean latency hides tail pain

Cloudflare found a 30–40% p99 improvement after a WAF change. Mean was nearly unchanged — no alert fired. "The 99th percentile is more relevant as a regular page load will likely hit that case at some point." A page with 70 requests hits p99 on at least one of them. Cloudflare Engineering, 2020

HTTP 200 hides application errors

GraphQL returns HTTP 200 for partial failures. A financial services team had a gateway generating 3,000–4,000 spans per request. HTTP showed all-green. The trace showed exactly which subgraph failed. "GraphQL will report HTTP 200, but the trace will show the error and where." OTel End-User Q&A, 2023

Part 1
Sampling

Choose your strategy based
on what you can afford to miss.

Always-on

Record 100% of traces. No decision made.

management: tracing: sampling: probability: 1.0

✓ Complete picture

✗ Storage cost scales with traffic

This workshop. Dev and staging.

Head-based

Decision at trace start. Random coin flip — propagated via the sampled flag in traceparent.

✓ Simple, low overhead

✗ Can't keep rare errors you didn't know were coming

High-volume production.

Tail-based

Decision at trace end. Buffer all spans, then decide based on outcome.

policies: - name: errors type: status_code status_code: { status_codes: [ERROR] } - name: slow type: latency latency: { threshold_ms: 2000 } - name: baseline type: probabilistic probabilistic: { sampling_percentage: 5 }

✓ Keeps all errors + slow traces

✗ Must buffer spans in memory; all spans of one trace must hit the same collector

Production recommendation.

Instrumentation

04
Part 1
Spring Boot · Micrometer Observation

One @Observed gives you
a metric and a span for free.

@Observed(name = "fx.call") fun getRate( @ObservationKeyValue("route.type") routeType: String, ... ): FxRateResponse { Span.current().apply { // enriches AFTER span starts setAttribute("fx.source_currency", sourceCurrency) // span only setAttribute("fx.rate", response.rate) // span only } // thrown exception → auto ERROR status + timer tag error=ExClass }

Thrown exceptions are automatic. @Observed catches any throw, calls observation.error(ex), sets span status ERROR, and tags the timer error=ExceptionClassName. You only set status manually for business rejections that return normally (e.g. a declined payment that doesn't throw).

The stack in this project

1. Micrometer — what you write

@Observed + ObservedAspect. Spring Boot auto-configures the registry.

2. OTel SDK — runs under the hood via bridge

You never call it to create spans — only to enrich them: Span.current().setAttribute(...)

3. OTel Collector → Tempo → Grafana

Receives OTLP, stores spans, powers TraceQL queries.

How metrics and tracing connect

One @Observed fires two handlers simultaneously:

@Observed ─┬─→ Timer fx.call.duration p50/p95/p99, count
│             ↑ exemplar: stores a trace_id on the metric data point
────── └─→ Span "get fx rate" your setAttribute() values

In Grafana: see a p99 spike on the metric chart → click the exemplar dot → jumps to the exact trace that caused it.

Why does cardinality matter? As a metric label, a high-cardinality value (like fx.rate=5.3842) creates a new time series per unique value — Prometheus explodes. In a trace, high cardinality is free. So: debug values → span only. Dashboard/alert values → keep them low-cardinality.

Never: PII · secrets · tokens · unbounded free text

Part 1
Three building blocks

Use the right primitive — span, event,
or link — for each situation.

Child Span

A distinct sub-operation with its own duration worth measuring.

@Observed(name = "fx.call") fun getRate(...) { ... }

Use when: calling another service, running a DB query, executing a business operation with meaningful latency.

Span Event

Something that happened at a point in time within a span. A timestamp + name + optional attributes.

// OTel Span API Span.current().addEvent( "cache.miss", Attributes.of( stringKey("cache.key"), key ) )

Use when: logging an exception, recording a cache miss, marking a routing decision — anything that happens inside an operation, not a sub-operation.

Span Link

A causal relationship between spans that are not parent-child.

// When processing a batch: // one consumer, many producer spans span.addLink(SpanContext.create( producerTraceId, producerSpanId, ... ))

Use when: batch processing (many producers → one consumer), async messaging fan-in, deferred jobs triggered by a previous trace. A parent-child would create a false single parent trace.

Span naming — from the OTel specification

A span name describes the operation class,
never the instance.

The exact OTel rule: "A span name SHOULD be the most general string that identifies a statistically interesting class of Spans, rather than individual instances."

Span nameVerdictWhy
getToo generalMeaningless — can't aggregate
get_account/42Too specificHigh cardinality, 42 is an instance
get_accountGoodaccount_id=42 as attribute
get_account/{accountId}Also goodTemplate placeholder convention

Source: OTel Trace API specification (stable, opentelemetry.io)

Applied to this workshop

get-EUR-BRL-route-721 instance baked in
fx.call stable operation name ✓
TransferService.prepare class name, not operation
pricing.calculate domain operation ✓

The rule in one sentence

The name describes the operation. Attributes describe the instance.

Part 1
Attribute naming — OTel semantic conventions

Reuse existing conventions first.
Define custom ones only when you must.

OTel semantic conventions — use these

// Infrastructure — always prefer OTel semconv http.request.method // not "httpMethod" http.response.status_code // not "responseCode" db.system.name // not "databaseType" messaging.system // not "queue" error.type // not "exceptionClass" server.address // not "targetHost"

Custom domain attributes — when OTel doesn't cover it

// Dot-namespaced, lowercase, snake_case words transfer.id // high-cardinality transfer.target_currency // low-cardinality pricing.strategy // low-cardinality pricing.route_candidate_count // low-cardinality fx.provider // low-cardinality

The naming rules (from the OTel naming spec)

→

Lowercase. transfer.id not Transfer.ID

→

Dot namespaces. Domain prefix, then property: pricing.strategy not pricingStrategy

→

Snake_case within components. transfer.target_currency not transfer.targetCurrency

→

Be precise. file.owner.name not file.owner

→

Never rename silently. Renaming an attribute breaks existing dashboards, alerts, and queries. Deprecate with a migration path.

→

Custom namespace prefix. For company-internal attributes: com.wise.transfer.id avoids clashing with future OTel conventions.

Dos &
Don'ts

06
Part 1
What to do

Instrument meaningful boundaries.
Keep everything low-noise.

Instrument at meaningful operation boundaries

Service calls, DB queries, business operations — anything that would appear in a sequence diagram for your domain. Not every function.

Add business context as attributes

Span name alone rarely tells you which input triggered the problem. Attributes like pricing.strategy and transfer.amount are what let you find the affected requests.

Thrown exceptions set ERROR status automatically

@Observed catches any throw and calls observation.error(ex) — span status becomes ERROR, timer is tagged error=ExceptionClass. You only need to set it manually for business rejections that return normally without throwing (e.g. a declined payment returning a result object). Use Span.current().setStatus(StatusCode.ERROR, "reason") for those.

Use @ObservationKeyValue on parameters for start-time values

With @Observed, the span already exists before your method body runs — you can't add attributes "at creation" from inside the body. Instead, annotate method parameters with @ObservationKeyValue("key"): those values are captured at span start and can become metric tags and influence tail samplers. Values computed inside the body via Span.current().setAttribute(...) enrich the span only — which is fine for tracing, but they miss the timer and the sampler.

Prefer OTel semantic conventions

Use http.response.status_code not responseCode. Standard names make your traces queryable by anyone and compatible with every observability backend.

Keep tail sampling in production

Always keep 100% of ERROR spans and slow traces. Drop healthy fast traces. Netflix's lesson: <1% of traces are ever looked at — store that 1% well.

Part 1
What not to do

More spans ≠ better observability.
More noise = harder to find the signal.

Span explosion — wrapping every function

A financial services team disabled HTTP auto-instrumentation entirely because it added hundreds of spans per request with no diagnostic value, drowning useful business spans. Instrument operations, not implementation details. OTel End-User Q&A, 2023

High-cardinality data in span names

OTel default limit: 128 attributes per span. But span names are indexed differently — every unique name is a new bucket in your trace backend. get-rate-EUR-BRL-route-721 creates unbounded index entries. Put variable data in attributes.

PII or secrets in span attributes

Trace data is indexed, queryable, and retained. Names, account numbers, auth tokens, API keys — none of these belong in span attributes. Breaches telemetry isolation and likely violates GDPR and internal data policies.

Tracing as a log replacement

Traces show structure and timing. They don't show detailed line-by-line context — what the exception message said, what the SQL query returned, the full stack trace. You still need logs for that. Traces and logs complement each other.

Part 1
TraceQL — Grafana Tempo's query language

TraceQL selects spans the same way
SQL selects rows — with conditions.

Curly braces { } select spans. Conditions filter them. A pipeline | aggregates the result.

Two scopes: span attributes vs resource attributes

// span. → attributes on the span itself { span.http.response.status_code >= 500 } // resource. → attributes on the service (host, version, env) { resource.service.name = "pricing-service" } // intrinsics — duration, status, childCount (no scope prefix needed) { duration > 2s } // this span's duration { status = error } { span:childCount > 10 } // direct child span count { trace:duration > 5s } // whole trace incl. async jobs

Combine conditions

// AND within one span { resource.service.name = "frontend" && name = "POST /api/orders" && duration > 2s } // AND across different spans in the same trace { resource.service.name = "frontend" } && { span.http.response.status_code >= 500 }

Where to write queries in Grafana

Grafana → Explore → Tempo data source

Select "Search" tab for the query builder, or "TraceQL" tab to write queries directly. The Workshop dashboard also has pre-built panels with TraceQL already configured.

Part 1
TraceQL — power queries

Aggregates and structural operators
find patterns no log query can.

Detect N+1 — too many identical calls

// Find traces with >3 spans hitting the same endpoint { span.http.method = "POST" && resource.service.name = "screening-service" } | count() > 3

Find fan-out — high child count

// Spans spawning more than 10 children { span:childCount > 10 } // Group by service to find the worst offenders { span:childCount > 5 } | by(resource.service.name) | count()

Structural — API call that touched the DB

// Descendant operator >> : find traces where // a specific API endpoint reaches a specific DB { span.http.url = "/api/orders" } >> { span.db.system = "postgresql" }

Find the last error in a cascade

// Not-child !< : leaf error span // (the root cause, not a symptom) { span:status = error } !< { span:status = error }

Env isolation check

// Find traces that crossed prod AND staging // (misconfiguration / data leak check) { resource.deployment.environment = "production" } && { resource.deployment.environment = "staging" }

In Grafana Explore → Tempo

Paste any query into the TraceQL tab. Results show matching traces; click any to open the full waterfall. Use the time range selector to scope to the incident window.

Bug 2 — The code

RiskController.kt:53 — no dedup, no blank filter

// "urgent payment, urgent transfer, payment reference" val terms = memo.split(",") .flatMap { it.split(" ") } .map { it.trim().lowercase() } // → ["urgent","payment","","urgent", // "transfer","","payment","reference"] // → 8 iterations: 2 empty + 2 duplicates terms.forEach { term -> screeningClient.check(term, customerId) // ← runs 8 times, 4 of them wasteful }

The code looks like correct per-term screening. Without the trace, you'd never know it ran 8 times when 4 were enough.

The fix — two lines

val terms = memo.split(",") .flatMap { it.split(" ") } .map { it.trim().lowercase() } .filter { it.isNotBlank() } .distinct() // → ["urgent","payment","transfer","reference"] // → 4 calls: all distinct, all meaningful terms.forEach { term -> screeningClient.check(term, customerId) }

After the fix: 4 sibling spans in the trace. The red duplicates disappear. Confirmed without reading a log.

Trigger: memo != null + targetCurrency = USD + amount ≥ 10000. Standard traffic almost never sets memo — so this is rare in production, invisible without traces.
